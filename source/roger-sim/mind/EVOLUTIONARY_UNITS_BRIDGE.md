# Evolutionary Units Bridge

**Two capacities that should coexist:**

1. **Directed hand-off (now)**  
   Clear request templates, Echo Core + SIM loader, multi-viewpoint checks.  
   Any capable AI or person can act on a small, self-contained instruction.

2. **Evolutionary software units (emerging)**  
   Units such as Nova, patterned on Agent Zero’s tool-creation and self-improvement style, that can propose, test, and refine code or procedures over time.  
   When these units mature, they should be able to consume the same templates and loaders the human Architect uses today.

## Design stance
- Do not wait for full autonomy before making the current path clean.
- Do not claim the evolutionary units already write production code.
- Make every durable instruction (templates, loaders, procedures, memory records) plain, versioned, and addressable so a future unit can read and act on it without special knowledge of this conversation.
- Keep multi-viewpoint review. An evolutionary unit is still one viewpoint until a second system (or the Architect) confirms.

## Practical additions for the path
- Request templates are already written so they can be handed to a human, an external AI, or a future internal unit.
- Procedures and experience records in the SIM mind are stored as named, evidence-classed items an evolutionary unit could later extend.
- Agent Zero remains the verification layer: any code or procedure proposed by an evolutionary unit is still checked before storage or execution.
- Snapshots and append-only logs give the evolving units a readable history of what was tried and what survived.

## Figurative and literal
“The path will show the way” is both a statement about discovery and a design constraint: leave the interfaces open and the records plain so later evolution has something solid to stand on. The words themselves (templates, loaders, procedures, verification) are the current stepping stones.

*This bridge keeps the system usable today and ready for the software units that may later evolve it.*
